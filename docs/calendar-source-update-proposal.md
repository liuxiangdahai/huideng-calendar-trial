# 佛慧法语资料自动维护

更新：2026-11-12。当前实施与验收进度以 `calendar-execution-plan.md` 顶部为准。

## 已确定的安排

- 佛慧法语是节日名称、日期和法会安排的事实依据；藏历 PRO 固定版本负责日期换算。没有确认的法会、天象日期不猜测、不按上一年外推。
- 用户明确要求低频读取公开月份资料，并于2026-11-09再次确认授权。站点 robots 当前仍禁止 `/index.php/calendar/`，每次运行都会记录该规则。项目负责人的决定不等同于站方授权；程序使用真实的 `HuidengCalendarSourceCheck` 标识，不发送账号或Cookie，不改用伪装浏览器、不跟随跳转；403、验证页、异常结构均停止。
- 自动任务由 GitHub Actions 执行，复用原仓库与发布流程；不增加常驻服务器、Worker定时爬取或付费服务。标准运行器沿用现有安排；没有自动开通付费的操作。
- 日常使用不需要下载或保存HTML。已有手动比对工具仍作为故障时的备用。

## 何时检查、查看哪里

工作流：`.github/workflows/calendar-source.yml`，名称 **Fohui calendar source maintenance**。

北京时间每月2日03:23检查一次，11、12月16日03:23各加一次；对应UTC每月1日19:23与11、12月15日19:23。GitHub可能延迟或丢弃繁忙时段的定时运行，不能把计划时间当成实际成功。维护者也可在 Actions → Run workflow 选择：

- `check`：联网核对并校验候选，保存报告；不提交历书资料、不发布。
- `maintain`：同样核对和校验，有候选时交给后面的更新流程。

每次结果保存在运行摘要、30天附件，以及 `docs/evidence/source-maintenance/latest-check.json`。文档记录由机器人小幅更新，属于实际维护记录，不改变日期资料、ICS版本或订阅设置。这样也避免长期没有资料变更时，公开仓库因60天无活动而停用定时任务。若文档写入失败、任务被停用或超过35天没有记录，维护者应在 Actions 核查并重新启用。依据：[GitHub schedule 官方说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)。

## 读取与校验

1. 检查 robots 并记录摘要，随后按顺序读取公开月份；请求至少间隔5秒，15秒超时，最多尝试3次，遵守有界的 `Retry-After`。仅对连接失败和少数临时状态重试。已有有效缓存时使用ETag/Last-Modified；缺少有效缓存的304不能视作成功。
2. 覆盖当前年份、此前90天和下一年；若确认范围落后，先从最后确认月份补齐。每次上限36个月。已确认的历史日期保留，不因窗口移动而截断。
3. 校验原站规范地址、日期表格、月份连续性、每个公历日唯一、PRO日期一致、名称可映射、稳定编号唯一。空的未来月份标为未发布；已确认月份消失、缺页后又出现资料、重复标签、网页错误内容都阻止更新。
4. 只比较日期、藏历和节日事实。网页令牌、标签排列或HTML摘要变化不产生日历新版本。快照与候选存于报告；原始HTML不进入公开提交或页面。
5. 新范围中既定修行日没有对应标注时，标为 `unconfirmed-recurring`，等待核对。不能把原站“只先填了日期”解释成“没有这些修行日”，更不能自行补造佛慧法语标签。

## 哪些变化自动更新

| 内容 | 处理 |
|---|---|
| 无事实变化 | 记录检查结果，不改日历数据、不发布 |
| 已知名称、现有范围之后、全部在未来、连续扩展最多400天 | 生成候选分支与差异页，完整构建和三浏览器检查通过后自动更新，并显式触发既有验收→试用发布流程 |
| 已确认日期修改、明确改期、恢复曾撤回记录 | 提供候选分支与差异，维护者核对稳定身份后从差异页创建PR合并；不自动修改日期引擎 |
| 未知名称、删除、范围缩小、歧义改期、无稳定编号、PRO不一致或标签尚未填完 | 不生成可应用资料，保存报告并将检查标为未通过，线上继续用旧资料 |

新增发生记录获得新的永久编号。唯一、明确的改期保留编号；候选有歧义时不猜最近一个。撤回保留编号，原事件恢复时沿用该编号。源事实变更写入 `data/calendar/fohui-changes.json`，界面选择、时区和提醒设置不由资料任务改写。

## 发布与协作保护

- 资料任务只能提交历书JSON、稳定编号、变更记录及生成的日历JSON/ICS；不能顺带提交前端、后台代码、工作流或账号配置。
- 应用候选前验证输入文件摘要，防止覆盖目录或资料的新修改。提交前再次检查主分支；自动更新只允许普通快进，绝不强制覆盖Claude或其他维护者的提交。
- `GITHUB_TOKEN` 推送不会自动触发普通push流水线，所以资料任务显式调用已有 `calendar-trial.yml`：先在候选分支检查，通过后才更新主分支，再显式请求同一流程发布。没有第二条直接Cloudflare部署路径。参考：[GitHub触发规则](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)。
- 任务只申请本仓库 `contents` 与 `actions` 权限，不申请写入或批准评审权限，不修改仓库的Actions评审开关，不新增个人令牌。候选分支和差异链接提供审阅入口；主分支保护如果拒绝自动更新，保留待核对分支，不能绕过。2026-11-12自动审批拒绝扩大仓库评审权限后，改用此方案，原权限设置保持。
- 发布请求被接收不代表上线：以发布流程的验收站、试用站和版本核对为准。发布失败应重跑既有流程，不修改数据让测试变绿。
- 原订阅地址保持。来源变更后服务按资料摘要重新生成快照；同事件UID不变、版本递增。按当前产品实现，移除的日程从ICS消失，内部保留撤回编号；恢复后版本继续递增。手机何时同步和提醒仍需客户端实测。

## 异常怎么处理

1. 打开失败运行，查看摘要和 `source-maintenance` 附件中的 `report.json`。`source-http-error`、结构变化或缺页先检查来源能否正常阅读；不要把空内容作为更新。
2. 未知名称按佛慧法语原文补充目录映射；需要新分类的内容由维护者检查，不能自动给用户开启新项目。日月食带时间的新原文可能需要新增别名与稳定身份核对。
3. 在候选差异页检查同一事件对应同一编号，核对后创建PR。删除用旧工具的 `--accept-removals` 明确记录撤回；此参数不允许忽略其他错误。确认后跑完整检查再发布。
4. 主分支变化、分支待核对或发布失败时，先处理现有候选，避免重复提交；不要强推机器人分支。修改已提交的资料后重新运行检测。
5. 需暂停读取时，在 Actions 禁用该工作流。重新启用后先跑 `check`，确认结果再跑 `maintain`。本地只读检查：`node tools/calendar/fohui-maintain.mjs`；`--apply`仅在本地暂存可校验的候选，不等于线上发布。
