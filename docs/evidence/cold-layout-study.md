复核日期：2026-10-28。结论：**尚无足够证据采用新的 CSS 优化；冷启动长任务仍未通过验收。** 本轮不改正式样式，也不将订阅可靠性修复的发布写成性能通过。

- 冻结正式发布 `35f4fdbecbfb4587543edeb7f4b505c055ed3352` 的静态文件，独立动态端口、本地 HTTP 与 gzip；不读取正在修改的源码。

- 2026-10-27 实验环境：Windows、i5-12500H、Chrome 156.0.8078.48，390×844、4 倍 CPU 降速、下行 1.6Mbps／上行 750Kbps、150ms 延迟。
- 每个变体仅完成 **1 次、开启 trace 的诊断采样**，未完成原定交错 5 次正式对照。不能排除 trace 开销、机器负载和缓存差异；不能直接与未开启 trace 的正式性能报告比较。
- 原始实验保留在本机 `artifacts/cold-layout-study/`，未将大体积 trace 和冻结网页加入仓库。

## 可支持的判断

1. 初次布局仍是主要调查方向。原页面 trace 中两次主要 Layout 为 379.2ms（336 个布局对象）和 293.0ms（29 个布局对象）；后续布局基本在几毫秒内。这不足以归因到某个具体控件。
2. 显式隐藏折叠分类没有减少该次主要布局的对象总数（仍为 336），没有证据证明重复隐藏原生 details 内容能解决问题。
3. 字体变体实际改变了标题字体和部分分类高度，但未达性能门槛，不能以牺牲已确认的视觉作为修复。
4. 快捷方案实验的 `min-height:99px` 被正式样式中更具体的 `.preset-card[data-preset]` 规则覆盖。该结果不支持宣称完整的预定布局变体有效。
5. 单轮基础点击检查可以展开分类、勾选、应用 54 项方案、进入预览并翻月；初始文档宽度均为 390px，未记录脚本错误。这不是完整三引擎、键盘或真实手机验收。

## 后续验收条件

先取得能指向具体布局或字体计算的证据，再提出最小改动。候选必须在同一固定构建、相同条件下完成原版与候选各 5 次无 trace 冷启动；另行记录 trace 诊断。验证视觉、CLS、分类展开、吸顶切换和长列表位置恢复后，才可合并。未满足条件前，执行计划中的冷启动性能保持“未通过”。
