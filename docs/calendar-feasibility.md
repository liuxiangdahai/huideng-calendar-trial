# 藏历订阅日历可行性复核

复核日期：2026-10-22。本文保留早期性能记录，最新快捷方案与提醒发布修正见末节。范围为当前仓库实现、已留存的测试记录及下列官方说明；没有部署生产服务，没有进行手机通知实测。

**这个方案可以做成长期使用的藏历订阅服务。现阶段可承诺的产品目标是：选择内容、固定订阅地址、持续更新日期；各手机是否按网页选择的时间提醒，需要分平台验收，不能作为已经实现的统一承诺。**

## 一、日期和目录：方案成立，资料维护必须持续

代码复核确认：底层固定使用藏历 PRO 提交 `c29e60f8292473c038a1da7d5a4061a3c97026fa`；七类 60 项、203 条公布记录。36 项具有明确固定规则，其余 24 项只使用已核对的公布记录。来源覆盖 2026-01-01 至 2027-05-06。已留存的逐日比对与测试覆盖 491 天、缺日、重日、闰月及跨年；这些证据支持已核对区间，不能证明未来几十年的所有节日安排都与佛慧法语一致。

36 项固定规则可在源资料之外继续生成；法会边界、节气和天象不会凭某年藏历日期推算以后。因此，**“未来 24 个月滚动订阅”表示服务窗口，并不表示所有分类的未来 24 个月均已补齐。** 如果以后不更新资料，荟供等固定日仍有日程，部分法会和天象会逐渐没有未来记录。避免臆造是当前实现的正确选择，但不能把“数据源更新失败时继续用上一版”理解成长期资料维护已经自动完成。

建议由小组指定资料核对人，至少每月检查佛慧法语新发布资料；上线前补核当前已公开的未来安排。更新须经过目录映射、日期比对、永久 ID 检查，再同时发布页面与 Worker。内部应记录各类实际覆盖、最后成功核对、候选更新失败和未来记录不足，并提醒维护人；这些维护信息无需堆在用户主界面。新名称和未识别记录继续让构建失败，避免静默遗漏。

PRO 当前支持至 2051-02-11；按现有完整 24 个月窗口，接近该边界前就必须升级引擎或调整窗口策略。这不是本次近期上线的阻塞项，应留在长期维护清单。

## 二、全天日程与具体提醒：格式可行，手机行为要分别验收

当前每次发生单独生成全天 `VEVENT`，提醒写成 UTC 绝对时间的 `VALARM`；不依赖手机把藏历转换为公历。iCalendar 标准允许绝对提醒，且规定 `DATE-TIME` 类型的触发时间使用 UTC。因此“日程全天显示、当天 08:00 提醒”在文件格式层面成立。标准符合性仍不能证明各日历 App 都会保留和执行提醒。[RFC 5545：TRIGGER](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.8.6.3)

提醒绑定用户选择的时区。选择温哥华 08:00 后，即使本人旅行到上海，提醒仍按温哥华时间发生；全天日期保持原日。若用户期望随手机所在地移动，应主动修改提醒时区，本版没有自动跟随手机时区的后台能力。

| 平台 | 官方已确认 | 当前可以支持的说法 | 尚需实际验证 |
| --- | --- | --- | --- |
| iPhone / Apple 日历 | 支持外部只读 ICS 订阅，也提供订阅日历的事件提醒开关 | 可以提供直接订阅入口，是优先验收的平台 | 全天条目的 UTC 绝对提醒、双提醒、仅显示不响铃、更新和撤销实际效果 |
| Google 日历 | 电脑网页可通过网址添加日历；提醒设置具有用户个人属性 | 持续订阅日期，不承诺网页逐项时间自动生效 | 当前账号对外部订阅提供哪些通知选项、手机同步、是否保留或替换 VALARM |
| 华为日历 | 所查适用机型说明支持 ICS / VCS 文件导入 | 支持的设备可使用文件导入备用 | 具体应用版本是否支持网址订阅、是否保留提醒；导入文件不会持续更新 |
| OPPO / 小米等 | 本次没有取得足以涵盖各版本的官方通用订阅证明 | 按实际日历能力选择网址订阅或文件导入 | 应用版本、导入/订阅入口、后台通知和更新行为 |

Apple 官方明确支持订阅日历提醒开关，但没有在该说明中承诺任意 ICS 的双 `VALARM` 都按原样执行。[Apple：设置多个日历](https://support.apple.com/zh-cn/guide/iphone/iph3d1110d4/ios)

Google 的网址添加流程在电脑完成。其通知教程中的按日历调整说明针对自有日历；不能据此要求所有外部订阅都出现相同设置，也不能断言 Google 在所有情况下都不提醒。[Google：网址订阅](https://support.google.com/calendar/answer/37100?co=GENIE.Platform%3DDesktop&hl=zh-Hans)、[Google：通知设置](https://support.google.com/calendar/answer/37242?hl=zh-Hans)

华为此文档证明的是文件导入能力，不是任意 HTTPS 日历网址的长期订阅能力。[华为：管理日程](https://consumer.huawei.com/cn/support/content/zh-cn16070813/)

用户取消选择后，服务会输出同 UID 的撤销记录；手机是否及时读取及移除旧提醒由客户端决定。90 天撤销保留期不能保证长期离线超过 90 天的客户端都能正确消除旧缓存。即时停用的可靠用户动作仍是在手机移除该订阅。

## 三、订阅后台：架构可行，免费额度尚未验收

Hugo 提供界面、Worker 生成个人订阅、D1 保存匿名设置与发布记录，适合当前小组规模的实现方向。读取和管理凭证分离、严格输入校验、稳定 UID、乐观并发控制及取消记录均已有实现。已有本地 SQLite 和 Cloudflare 本地 D1 检查证明接口可以工作，不证明云端容量、跨境访问和手机同步已经合格。

本轮重点发现是生成成本：每次 GET 或 HEAD 都先计算日期、提醒和内容摘要，再判断 ETag。即使最后返回 304，也已经做了主要计算和发布版本写入。当前 ETag 能节省响应传输，不能当作生成结果缓存。

本轮优化后，本机 Node.js 24.15 / Windows 连续 7 轮测得，仅“日期生成 + ICS 序列化”的耗时如下；不包含 D1 请求和逐项发布摘要：

| 选择 | 日程数量 | 耗时中位数 | 测得范围 |
| --- | ---: | ---: | ---: |
| 旧版两项荟供设置（现默认仅莲师） | 56 | 6.7 ms | 5.4–41.1 ms |
| 全选，每项两次温哥华提醒 | 301 | 23.5 ms | 22.2–26.4 ms |

这些是本机经过时间，包含运行时调度；不是 Cloudflare CPU 计量，不能直接拿来计算线上额度或容量。它们足以说明仍需性能验收，不能因为本地响应成功就认定免费套餐可用。

Cloudflare 官方当前给 Workers Free 的每次 HTTP 请求 CPU 限额为 10 ms；网络和数据库等待不计入 Worker CPU。付费方案有更高 CPU 额度。生产须记录冷启动、默认设置、全选双提醒、重复刷新、304 和并发修改的 CPU 与总耗时，检查高分位数和资源超限。[Workers 限制](https://developers.cloudflare.com/workers/platform/limits/)

当前变更写入使用 JSON 批量语句，不是每个事件单独一次 SQL；301 个事件不等于 301 个 D1 调用。D1 免费版每次调用最多 50 条查询、单库最多 500 MB，单库串行处理查询。日历规模能否承受应看实际查询时长和并发，不按事件数量直接判定。[D1 限制](https://developers.cloudflare.com/d1/platform/limits/)

D1 免费额度当前为每天 500 万行读取、10 万行写入；索引也可能增加写入计数。首次发布、修改全部提醒、日常刷新和墓碑清理的成本不同，不能只按订阅人数估计。使用实际 `rows_read`、`rows_written` 和存储指标评估。[D1 计费说明](https://developers.cloudflare.com/d1/platform/pricing/)

建议生产采用以下顺序：先在选定套餐下完成云端压力与 CPU 检查；若目标是免费运行，再优先增加持久生成缓存，用“设置版本、资料版本、提醒时区的当前日期”作失效条件，让未变化的 GET / HEAD / 304 尽早返回。不能只靠进程内缓存保证性能，因为 Worker 隔离环境会被回收。若采用付费套餐，也仍需监控突发请求、D1 写入和长期发布记录增长。

本轮审计还定位并修正了过期墓碑的重复清空写入：每次请求和每日清理现仅匹配仍有内容的记录，跳过已经清空的条目；这降低长期写放大，不改变 UID / 序号保留策略。已复核两处 SQL 均加入该条件。

## 四、上线前应完成什么

1. **服务接通：**配置小组持有的 HTTPS 域名、生产 D1、允许的网站来源和私有盐；保存、读取、修改、停用及旧地址刷新均从正式网站验收。当前移除界面的体验说明，不代表服务已经上线。
2. **手机验收：**至少一台 iPhone、一台使用 Google 日历的 Android、以及小组实际使用的一种华为 / OPPO / 小米日历。记录系统和 App 版本、订阅方式、日期显示、一次/两次提醒、静默条目、网页修改后的刷新、撤销、断网恢复和时区差异。关闭网页后仍能通知才算完成提醒验收。
3. **访问与运行：**在小组实际网络环境测试网站和订阅域名；选择免费或付费运行方案，并完成上述 CPU / 数据库指标检查。免费额度未经验证前不作“永久免费运行”承诺。
4. **资料运营：**指定核对人和更新频率，核对未固定的未来安排；落实内部失败提醒、备份与回滚。Cron 现在负责清理，不负责抓取新藏历资料。

一期继续保持 Google 通用订阅、无 OAuth 的范围是合理的。如果以后把“所有平台均按网页逐项设定时间准时通知”设为硬要求，需要另立提醒同步方案。即使以后加入 Google API，也要专门设计全天事件当天提醒：API 的提醒分钟数是开始前的 0–40320 分钟，不能简单用负数表达全天开始之后的 08:00。[Google：提醒概念](https://developers.google.com/workspace/calendar/api/concepts/reminders)、[Google：事件提醒字段](https://developers.google.com/workspace/calendar/api/v3/reference/events)

当前结论是：**可以继续按正式项目推进，并先发布完成真机验收的平台能力；统一跨平台精确提醒、长期完整资料和免费生产运行，仍分别需要手机、维护流程和云端性能证据。**

## 2026-10-22：快捷方案与提醒发布复核

现有 Hugo + 藏历 PRO + 佛慧法语资料 + Worker/D1 匿名订阅架构继续可用。此次没有新增会员系统、接口版本或数据库表。主要变化与复核结果如下：

- 新用户只默认莲师荟供日当天 08:00；旧 v1/v2 选择与各自提醒保留。三种快捷方案是一次性选择，第三种当前 54 项；明确排除四项节气及其他纪念日，包含已收录的四类日月食。目录中的 eclipse / solar-term 标签区分天象与节气，未来新增节气不会被误选。

- 中国显示北京时间，内部仍为 Asia/Shanghai。海外首次采用设备时区，已有地区保留。设备时钟优先，跨区显示两地时间、跨日日期；同一设备时刻计算，不做网络校时或定位。具体日程另按发生日期计算设备当地提醒，避免用当前时差替代未来夏令时规则。

日程卡、时间比较和方案属于前端；最终提醒发布属于后台。两端必须一起发布，静态页改好不能证明云端已更新。订阅凭证继续分离，浏览器只保存匿名管理凭证，换设备依赖管理链接。
