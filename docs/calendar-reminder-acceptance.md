# 提醒专项验收记录

更新：2026-11-04。此文件区别程序检查、用户反馈和真实通知；没有手机证据的项目不判通过。

## 现状与用户反馈

- 上一技术发布 97778a2：日程显示正常；用户反馈各日历详情未见提醒时间。
- 本轮确认：iPhone iOS 27.0.1，Event Alerts 已开启；日程详情仍未见具体提醒字段。尚无单/双提醒按时弹出的记录。
- 现有正式链路按保存的 `mode=remind` 生成全天事件和绝对 UTC `VALARM`。本轮未以猜测更换正式提醒格式。
- “十分钟导入文件”只是导入/系统权限辅助检查，不能代替持续订阅验收。

## 隔离测试入口与操作

入口（部署验证后方可交付）：https://huideng-calendar-acceptance.pages.dev/calendar-reminders/reminder-check.html

1. 在 iPhone Safari 打开，填写设备版本，检查设备时区。点击准备后约30分钟开始；用户自己决定何时开始，不提前创建会过期的个人测试地址。
2. 添加“慧灯提醒测试”独立日历，确认 Event Alerts 和系统通知；不要为整个日历统一开启默认通知。
3. 手机中看到全部测试日程及轮次后，再在网页确认“我已在手机看到本轮日程”。临近或错过测试时间，应重新安排一轮并等待同步。
4. 关闭网页、锁屏观察。记录实际通知时间，未收到与尚未同步分开；E/F 应保持无通知。
5. 使用同一地址再测一轮、次日08:00跨天一轮。旧记录留存。再核对改时间、仅显示、取消、停用，不能靠立即删除日历代替撤销验证。
6. 导出本机观察记录。记录不含 feed/manage 凭证；自由输入文字仍应避免粘贴个人订阅链接。完成后在手机移除测试日历。

| 项 | 实际写法 | 应有通知 |
|---|---|---|
| A | 正式同款全天事件 + 绝对 UTC 提醒 | 起始时间一次 |
| B | 全天事件 + 相对当天零点的提醒 | 起始后3分钟一次（保持手机时区一致） |
| C | 定时事件 + 开始时相对提醒 | 起始后6分钟一次 |
| D | 全天事件 + 两个绝对 UTC 提醒 | 起始后9、12分钟各一次 |
| E | 全天仅显示事件 | 无 |
| F | PRO 每日藏历，标记为测试 | 无 |

B 的相对 DATE 提醒按客户端时区解释，不能替代固定提醒时区语义。C 只用于诊断，不把正式修行日改成具体开始时间。测试使用现有创建/管理接口、独立验收 D1、稳定 UID、版本台账、快照和 Pages 服务绑定；不新增数据表。试用构建拒绝 `reminderProbe`，不发布测试页。测试72小时到期，随后取数生成撤销；客户端未同步时仍需手动移除。

验收要求：至少三轮，含一次跨天；正常系统设置下目标时间误差≤60秒。单、双提醒按次数出现；静默项目零通知。改期、取消和停用须先确认手机已同步相应版本，再判断是否存在旧通知。48小时未同步则该项目不通过。观察四个时刻：网页保存、服务端更新时间/检查、手机确认同步、实际通知。网页确认按钮是用户报告，并不是后台已获知客户端状态。

## 决策规则

- A 通过：保留正式格式，继续查不同客户端设置/同步和双提醒。
- A 失败、B 通过：定位为可能的绝对提醒兼容问题；继续跨时区验证，不直接替换正式格式。
- 全天 A/B 失败、C 通过：可能与全天提醒有关；如需改变产品表现，提交实测证据后再决定，不自行添加定时副日程。
- A/B/C 均失败、手动本机日程通过：重点查订阅提醒的接收/保留与客户端限制。
- 手动本机日程也失败：先检查系统通知、专注模式、摘要、声音设置；不能据此判断订阅格式不支持。
- 日程未同步：只记录同步失败，不能记为提醒格式失败。

## 已知限制

当前没有代码可从网页读取 iPhone 的日历详情或系统通知结果。必须由持有真机的测试者观察反馈。CPU、冷启动、免费额度等既有未达标项没有因本轮测试而变为通过。不增加账号授权、额外通知渠道、付费服务。

依据：[Apple 订阅日历日程提醒](https://support.apple.com/zh-cn/guide/iphone/iph3d1110d4/ios)、[iCalendar TRIGGER 标准](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.8.6.3)。标准允许某种格式，不等于具体系统版本执行了通知。
